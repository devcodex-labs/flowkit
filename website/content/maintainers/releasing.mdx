# 发布维护

此页仅供具有仓库与 GitHub Packages 发布权限的内部维护者使用。FlowKit 是内部运营的专有基础设施，未来客户通过托管 MCP/API 或付费工作流设计服务使用能力，不向客户提供 npm 包。内部软件包只发布至 **GitHub Packages 私有 npm Registry**，不再向 npmjs 发布。包名为 `@devcodex-labs/flowkit`，Registry 为 `https://npm.pkg.github.com/`。

## 不可跳过的流程

冻结 Commit 与版本 → 运行 CI（SDK/类型/12+E13 文档消费者）→ 核查候选 tarball 与 SHA256 → 通过 `publish.yml` 发布到 GitHub Packages → 用有读取权限的身份读取已发布精确版本 → 比对 Registry 下载包与已审阅 tarball → 构建并验证站点 → 依据批准的站点可见性策略部署。

**本页为操作规范，不表示候选版本已经发布。** 当前 `main` 的源码版本不等同于 Registry 已有版本；不能移动现有 Tag 或以重新打包代替原始发行字节。

## 准备候选

在 Node >=24 和获授权的工作区执行：

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm --prefix website ci --ignore-scripts --no-audit --no-fund
npm run verify
npm run docs:check
npm run docs:examples
npm run docs:build
npm run release:check -- --tag v1.0.0
npm run release:pack -- --tag v1.0.0
node scripts/release.mjs verify --tag v1.0.0
```

版本应与 package、lock、CHANGELOG 与 Tag 一致。此步骤只准备候选，不执行真实发布。检查 `.tmp/release/` 仅包含按白名单生成的 tarball 和 release.json，记录包 SHA256、成员、原 Commit 与构建环境。

## GitHub Packages 权限和发布

发布必须先经授权确认 LICENSE 草案和具体发布版本，再将仓库变量 `FLOWKIT_ENABLE_PACKAGE_PUBLISH` 设置为 `true`；默认关闭以防误发布。发布工作流只允许使用 `packages:write` 的 `GITHUB_TOKEN` 与正确的组织 Scope，配置 `actions/setup-node` 的 `registry-url: https://npm.pkg.github.com`。发布命令不得出现 `--access public` 或 `registry.npmjs.org`。首次发布后通过 `scripts/docs/check-package-privacy.mjs` 核实包的 **Private** 可见性及 Actions 访问授权；GitHub 仓库 Private 并不自动证明包权限正确。

消费方配置 scoped `.npmrc`，令牌由环境变量注入。仓库外消费者通常需要有 `read:packages` 的 PAT (classic)；Actions 从本仓库读取私有包可在适当授权下使用 `GITHUB_TOKEN`。不要在 GitHub Pages、日志或 GitHub Actions Artifact 中保存 Token。完整配置见[安装](/guide/installation)。

## 不可变发布与文档部署证据

`publish.yml` 的 preflight/CI/pack/publish/private-consumer 阶段必须全部成功；`docs.yml` 应核验原发布 Run/Attempt、`packageReleaseCommit`、`docsCommit`、Tag、tarball SHA256 与产物身份。原包与文档源可以是不同 Commit，但文档修订必须满足原白名单和祖先关系，不能借修订文档偷改已发布包。

从私有 Registry 执行 `docs:private-package`，必须验证确切版本的 `dist.integrity`、tarball 哈希、包名和版本，再运行全部教程消费者用例，不能把无访问权限的 `404` 当作包不存在或发布成功。

**公开文档站已获项目负责人批准**，目标地址为 GitHub Pages `/flowkit/`。GitHub 源码仓库当前公开，仓库可见性与许可证授权范围、GitHub Packages 的包权限分别核对。发行后须确认包为 Private。部署前须核对 Pages 权限、环境保护和公开内容边界。网站的搜索索引和 sitemap 公开，发布内容须排除凭据和内部资料。

## 失败与恢复

- 候选验证失败：不发布，不改原 Tag，不用跳过失败测试代替修复
- Registry 发布失败：先查实际版本与权限，避免对不可变版本重复发布
- Registry 消费失败：核查 token/scope/组织权限与下载字节，不只依赖 `npm view`
- 文档构建失败：保留原发布身份、tarball 与 Artifact，按允许的文档修复范围重建
- Artifact 过期：需要找回可验证原始字节，不能重包冒充原已发布产物

可通过 `npm run docs:check` 与 `npm run docs:build` 验证站点；站点公开已获确认，但**上线仍是单独的发布动作**：只有通过站点披露审查、权限核对与维护者批准后，才将仓库变量 `FLOWKIT_ENABLE_PAGES_DEPLOY` 设为 `true` 并部署。默认情况下文档发布任务不会部署 Pages。第三方依赖与其许可证不会因 FlowKit 改为专有软件而改变。
