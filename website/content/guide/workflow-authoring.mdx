适用 FlowKit 1.0.0 的编写与验证路径。先用[能力目录](/guide/capability-provider)找到与当前版本匹配的说明，再对照[工作流模型](/guide/workflow-model)与[编译诊断](/troubleshooting/compiler)。

本页为人类作者及开发宿主模型提供同一份编写依据。从业务目的选择现有能力，形成合法 DSL 和必要 Host 绑定，再检查业务结果。启用 Author 的宿主可以调用以下工作流编写路径。编译／检查和 Host 执行入口也可直接使用。

## 用本机 FlowKit MCP 起草、导出和添加

<a id="flowkit-doc-codex-plugin"></a>

首次从源码使用时，在仓库根目录安装依赖并构建。候选预览与 HTML 导出使用仓库自带的流程图模板。默认模型使用本机已登录的 Codex CLI。

```powershell
npm ci
npm run build
codex login status
```

在仓库根目录保存本机配置 `flowkit-mcp.local.json`。默认集合随数据目录保存，重启后继续使用同一个集合。凭证由操作者在客户端和服务使用的环境中预先设置为同一个 `FLOWKIT_MCP_TOKEN`，长度至少 24 个字符。每次手动测试只需启动这一个服务。

```json
{
  "listen": { "host": "127.0.0.1", "port": 8765, "mcpPath": "/mcp" },
  "dataDir": ".flowkit/data",
  "exportDir": "flowkit-exports"
}
```

复杂流程可选设 `authorTaskTimeoutMs`（单次模型任务，默认 90000 毫秒）和 `authorTurnDurationMs`（完整起草或复审回合，默认 240000 毫秒）。两项都使用正整数毫秒。宿主与 Codex 客户端各有自己的等待时间，调长宿主预算时也要让客户端的 `tool_timeout_sec` 覆盖整个回合。

```powershell
npm run mcp:local -- --config ./flowkit-mcp.local.json
```

启动输出包含 `url` 和一次性 `operatorUrl`。用常用浏览器打开 `operatorUrl` 建立本机会话。看到「操作员已连接」后回到 Codex 继续操作。客户端通过 `url` 使用 MCP，可直接配置连接，也可安装下文的纯 MCP 插件。直接连接时，在 Codex 的配置文件中设置：

```toml
[mcp_servers.flowkit]
url = "http://127.0.0.1:8765/mcp"
bearer_token_env_var = "FLOWKIT_MCP_TOKEN"
```

### 本机服务和模型配置

| 配置 | 默认值及用途 |
|---|---|
| `listen.host`、`listen.port`、`listen.mcpPath` | `127.0.0.1`、`8765`、`/mcp`。连接地址只允许本机回环。端口值 `0` 用于隔离测试的随机端口 |
| `namespace`、`workspaceId`、`defaultCollection` | `flowkit-local`、当前 `namespace`、`flowkit-workflows`。数据目录与这组身份绑定 |
| `dataDir`、`exportDir` | `.flowkit/data`、`flowkit-exports`。分别存放隔离的候选状态与导出文件 |
| `mcpTokenEnv` | `FLOWKIT_MCP_TOKEN`。指定服务读取 MCP 凭证的环境变量名，客户端用同一凭证 |
| `authorProvider`、`authorModelEnv` | `codex`、`FLOWKIT_AUTHOR_MODEL`。Codex 采用 CLI 登录态，`openai` 采用配置的 Responses 模型和 `OPENAI_API_KEY` |
| `authorTaskTimeoutMs`、`authorTurnDurationMs` | `90000`、`240000`。单次模型任务与整个 Author 回合的时间上限 |
| `trustedExportKeys` | 接收方接受的签名公钥。撤销源授权时，从该列表移除并重启接收服务 |

使用 OpenAI Responses 时，将服务配置中的 `authorProvider` 改为 `openai`，在服务环境中提供 `OPENAI_API_KEY` 和 `FLOWKIT_AUTHOR_MODEL`。操作仍使用同一个 MCP 入口。已有编译工作流由 SDK 或 Host 提供运行模型和授权。宿主角色、数据、业务回调、Task V2 资源预算及授权目录随 Host 配置传入。

### 安装纯 MCP 插件

构建产物为 `flowkit-mcp@flowkit-local`。面向 Codex 的包包含插件清单和 MCP 连接配置。使用非默认地址时可在构建前设置 `FLOWKIT_MCP_URL`。

```powershell
$flowkitPlugin = node scripts/build-codex-plugin.mjs | ConvertFrom-Json
codex plugin marketplace add "$($flowkitPlugin.marketplace)"
codex plugin add "$($flowkitPlugin.selector)"
codex plugin list --marketplace flowkit-local
```

保留已登记的 marketplace 目录，然后重开 Codex 会话。使用插件连接时，可停用同地址的直接 MCP 配置，避免重复注册工具。

### 从第一份草稿开始

1. 在 Codex 输入「用 FlowKit 起草一个核对导入文件的工作流。文件可读时核对字段，核对通过才返回结果。读取或核对失败时结束并返回原因。请复审候选并给我流程图预览」。有待决定的分支时，在原草稿补答。
2. 打开候选的预览链接。页面使用同次编译的 GraphSnapshot，核对步骤、分支和终点后确认候选。改稿后按新候选重新预览和确认。
3. 确认当前候选后要求导出。打开 `workflow.html` 即可离线查看与预览相同的流程图。概览的「阅读 Mermaid」和「阅读根契约」支持查找及放大文字。`workflow.mmd` 可交给 Mermaid 工具，`workflow.js` 可交给执行方。MCP 导出结果同时给出目录、文件链接及各自的 SHA-256。改稿后，使用新候选的预览链接重新复审和确认。

已经打开过候选但需要重新排版时，可以对 Codex 说「为这个候选重新排版，打开结果」。本机工具 `flowkit_relayout_workflow` 接收候选、当前布局版本和请求 ID，并返回新版预览链接。导出时使用该预览的布局版本。旧导出仍可按各自的摘要和签名核验。模型重排失败时，预览服务保留已选布局。

下载链接过期时，让 Codex 用原 `draftId`、`candidateHash` 和返回结果里的 `exportReceipt` 重新调用 `flowkit_export_workflow`。原候选和原文件仍可读取时，FlowKit 核验三个 SHA-256 后签发新链接，保留原 HTML 签名。此调用只传收据。要导出当前渲染版本，打开当前预览并使用它的 `layoutRevision`。原收据的文件内容改变或缺失时，补领会失败。

已有 Interactive 运行绑定的宿主可以在调用 `startLocalMcp` 时提供 `resolveRunViewer`。解析器接收运行 ID 与当前操作员的服务端请求上下文，返回该次运行的 `{ auth, ref, options }`。其中 `auth` 为请求范围内的受信 Host 能力，`ref` 绑定实际运行及其 Program 和 GraphSnapshot，`options` 提供原运行的策略、Store、Program registry 和同一 GraphSnapshot。操作员可打开 `/runs/<runId>` 查阅状态、激活次数和重试记录，并按修订翻页。在产物中心可筛选当前页授权产物的节点、类型、版本或生效状态，点击产物可回到来源节点。刷新与翻页都只读取运行。文件正文仍由宿主的授权存储接口提供。

宿主如需关联接收方的候选，可另外提供 `candidate`，并在 `ref` 中声明 `collectionId`、`candidateHash` 与 `approvalRef`。宿主应按这三项验证接收方的审批。页面还会验证候选文件及图摘要，才展示该候选和 Mermaid。导入可以生成新的候选身份，运行仍绑定原 Program 和 GraphSnapshot。

Standard 宿主可以通过同一解析器显示一次真实调用的 trace。启用编译 trace，使用 `runtime.trace.start` 和 `runtime.trace.end` 收集节点调用，再返回 `{ ref, candidate, standardTrace, authorizeTrace }`。`ref` 含运行 ID、候选、产物和图摘要，`standardTrace` 含运行结果 `status` 和 `events`。每条事件含 `nodeId` 和 `kind`，结束事件另有 `outcome`。`authorizeTrace` 必须根据当前请求身份和这些摘要授权。页面只展示节点的实际调用记录，持久日志和修订分页由 Interactive 提供。

宿主还可提供 `viewManifest` 添加节点说明。结构为 `{ schemaVersion: 1, graphDigest, nodeDescriptions: [{ nodeId, text }] }`。同时提供 `authorizeViewManifest`，依据当前请求、运行引用和清单核对资料读取权限。有效说明以纯文本展示；版本错误、未知节点或未授权时，页面仍显示原有编译视图。
4. 在同一个 Codex 会话说「把这个工作流添加到 FlowKit」。Codex 使用当前候选发起添加。打开返回的链接，核对候选名称和版本，再点「确认并加入 FlowKit」。回到 Codex 查看保存结果，或让 FlowKit 列出默认集合中的工作流。

起草时可以明确选择 Standard、Interactive P0-A、P0-B、P1 或 P2。需要持久 Action、人工确认及循环时选 P0-B，需要持久并行时选 P1，需要首个合格分支选胜时选 P2。请求中说明根输入的类型、必填业务输出及负责生成该输出的步骤。复审根据实际编译结果核对来源和失败边界。执行方用可信的产物 SHA-256 校验工作流，再通过 [Standard SDK](/reference/sdk#runArtifact) 或 [版本化 Interactive Host](/reference/interactive#start) 运行。

起草嵌套 P2 时，说明外层和内层各自的成功条件、每个校验器在 Host 中的实际名称，以及何时整体失败。例如「外层同时校验输入和复核结果。输入用 `check-input`。内层 `check-copy` 和 `check-original` 任选首个通过。输入不通过或两路复核都不通过时整体失败」。[子流程分支规则](/dsl/parallel)

起草 Interactive Action 时说明它是否会写入外部系统。只读回调可以把结果保存到工作流状态。Author 会核对计划与编译产物中声明的外部效果，复审时也会检查这一点。只读回调的 Host 回执使用无外部副作用结算。

如果起草中服务意外退出，用原数据目录重启。在 Codex 说「继续这份草稿」。草稿如显示需要对账，Codex 可调用 `flowkit_recover_workflow`，取回已持久保存的结果，或在核实旧 Author 执行权已失效且无外部效果后继续原草稿。存在未确认的外部写入时，需要 Host 先对账。一个数据目录同时只由一个本机 MCP 服务使用。

### 已有文件的备用导入

手上只有已有文件、Codex 没有候选或来源引用时，可用本机页面的「添加已有工作流」登记来源。当前 MCP 添加工具接收候选引用或已登记的来源引用。选择之前导出的三个文件，或选择可信的候选 JSON，点击「生成来源引用」，再把返回的引用交给 Codex 发起添加。

跨实例转交时，从导出方的启动信息取得 `exportPublicKey`，并通过已知可信的渠道核对。将该公钥加入接收方本机配置的 `trustedExportKeys` 数组，重启接收服务后登记原样的三个文件。HTML 内的签名同时绑定三个文件和来源，受信的 FlowKit 导出会默认进入接收方的 FlowKit 集合，仍须在接收方复审并确认。修改任一文件会使签名失效。首次使用此功能时，可从原实例重新导出旧候选以取得带签名的三文件。依赖专用 Skill、外部资料或已批准安全策略的候选须由 Host 处理依赖和批准。

从 `trustedExportKeys` 移除公钥并重启接收端后，此公钥此前登记的待添加来源和待确认链接都会被拒绝。已保存的版本和历史回执仍可读取。旧的待处理来源若未记录签名公钥，请重新登记原始文件。

转交同一工作流的新版本时，使用同一导出公钥及更高的工作流版本号。接收端核对源集合和工作流标识，复审并显示当前版本与待更新版本。确认后新版本才生效，旧版本继续保留。若另一版本已先生效，用新的添加请求进行复审。缺少旧版本签名来源记录时，先由接收方核对现有版本及可信来源。

如果外部工作流已有可安装的 Codex 插件，在登记来源时可填写已登记的插件标识。Codex 会列出可用去向。选择加入 FlowKit 时，服务会校验候选是否兼容。选择独立安装时，由 Codex 安装并确认结果。

### 自动验证与卸载

维护者可先构建当前代码，再用固定输入验证 CLI 连接和协议。已登录的 Codex CLI 可以运行真实模型验证。`--live --interactive` 起草真实嵌套 P2、复审并导出三个文件，随后从公开 SDK 验证首路通过、另一路接替、复核全失败和输入不通过。

```text
npm run build
node scripts/test-local-mcp-codex.mjs
node scripts/test-local-mcp-codex.mjs --interactive
node scripts/test-local-mcp-codex.mjs --live
node scripts/test-local-mcp-codex.mjs --live --p0b
node scripts/test-local-mcp-codex.mjs --live --interactive
codex plugin remove flowkit-mcp@flowkit-local
```

## 用 Author 准备 Workflow Skill

本机 MCP 的新建 Standard、P1 和 P2 草稿使用已校验的节点选项直接编译，再从同一张图推导控制边。真实业务缺项在原草稿中补答。Plan 和 DSL 共用两次自动技术修订，额度耗尽时保留最近的具体诊断，方便在原草稿修订。

Author 读取的文档 revision、来源 URI 和内容 Hash 随候选保存，编译前重新检查当前来源；过期或错版不继续编写。复审同时显示实际编译节点的语义差异和文件差异。可选 `references` 只接收工作流专属资料，禁止嵌套 Skill；默认三文件保持不变，不复制整套 DSL 文档。

能力和 `requires` 依赖必须全部适用，Graph 返回 complete 也不能把 unknown/partial/inapplicable 当作成功。编译出的控制边必须与当前 Plan 一致，不能因遗漏一条分支而绕过复审。自动 Human 修订必须有有限的 `maxRevisions`。`parallel.any` 包含 Action 或副作用未知的 Agent 时，需要 Host 为精确 Artifact 认可安全策略；缺失即拒绝候选，FlowKit 不新增协作取消或 winner-only 语义。

已明确的要求缺少 Plan 节点映射，或 DSL 与固定 Plan 图不一致时，AuthorHost 使用共享的有限技术修复预算。未确定的业务规则返回选项和推荐，用户在同一草稿补答后继续。

Plan 与编译器共用节点校验规则。节点 ID 使用 kebab-case，最长 64 字符。节点显示名最长 40 字符。Standard Loop 的 `onSuccess` 和 `onMaxExceeded` 要指向不同节点，并分别有对应的控制边。编译后仍核对两个出口各自的角色。
Standard Parallel 的成员各自只有一条通往汇合后节点的派生控制边。成员失败由并行运行语义处理。

对于无既有候选和外部基线的新建草稿，AuthorHost 使用原始请求与补答重建完整意图。Standard 草稿从已校验的 Plan 节点选项生成 DSL，控制边由编译器推导。候选继续绑定来源摘要并进入语义复审。
模型输出不合规时，在当前请求预算内可再解析一次。技术修复耗尽后，用户可在原草稿发起新一轮继续或原样重发补答，AuthorHost 保留已授权的上下文与选择。补答后的业务问题必须提供可选方案，技术诊断交给校验流程处理。
约束覆盖项可用 `constraintId` 指向精确的已授权约束。Plan 保存时统一为 `intentId`，冲突或未知引用会被拒绝。

集合发现目录按保存事务固定的完整批准快照生成，写文件前持久分配路径。映射须 CAS 和实际读回；失败如实 saved/discovery-pending，旧发布重试不反激活旧版。清理先撤映射、核 Run 无引用且新 Run 接入关闭，再核验全文件；用户增改、链接或所有权不符保留并对账。历史 Artifact 保留。配置与恢复见 [Author Host](/guide/host-integration#author-host)。

宿主可安装随包交付的 `dist/author/flowkit-workflow-author/SKILL.md`。启用前由宿主配置 Author、Intent Runtime、已授权的 Capability Graph、候选审查与执行授权。用户可以从一句项目目标开始，Author 沿用明确选择，针对会影响控制流或交付的未知项提供方案和推荐。

用户先核对候选目标、控制流和文件差异。Standard workflow 使用同一次编译的 `workflow.js` 与 `workflow.mmd`，与 `SKILL.md` 同目录。需要保留 DSL 时显式启用 `source/workflow.dsl.js`。Workflow Skill 与 Professional Skill 都出现在主集合的 `skills/` 目录下。集合逻辑 ID 在重命名时保持，旧版本继续保持原 Artifact 身份。
独立复审未通过时，草稿的 `reviewRejection` 与 `reviewCandidate` 的 `rejection` 提供同一候选的具体发现。Host 用新 turnId 和动作附带的 `candidateHash` 发起 `review-only` 重审原候选，或发起 `authoring` 按发现修订。改稿沿用原草稿的用户请求、补答及明确授权的基线。评审查看声明节点、Mermaid 渲染标记及 Parallel 控制语义，用户批准仍需单独记录。

宿主验证候选摘要与审批，发布完整版本并将获准的目录映射到发现位置。执行已有 Workflow Skill 时，宿主核对下载或本地文件与已批准 Artifact、固定资源版本和当前权限，再经 [runArtifact](/reference/sdk#runArtifact) 执行。Standard 运行无需安装 Author。

## 从业务目的到可执行交付

候选节点详情显示执行者类型、业务角色和关联 Skill。Agent 步骤确实需要可复用指令时，Author 先查询当前集合和 Host 授权的目录。本机先按准确 ID 或名称查找，再按用途查找异名 Skill，在预算内检查批准版本的正文是否满足本次需要。找到一个适用版本时预选原版本。多个匹配、正文适用性无法确认或目录查找超出预算时保留待处理项。完整搜索确认没有匹配时才起草。候选预览可复审草稿，确认加入集合后保存工作流及准确的 Skill 版本。执行权限仍由 Host 按实际身份核验。

签名三文件可携带 Professional Skill 的逻辑来源、ID、精确版本和摘要。接收端可以先查看和复审。缺少授权依赖时预览给出原因，`@devcodex-labs/flowkit/host` 的 `runApprovedCollectionWorkflow` 拒绝运行。同一集合使用批准仓库的精确版本。跨宿主通过 `resolveRunProfessionalSkill` 返回经授权的准确源候选，由 FlowKit 重验实物和版本后才派发。私有 Skill 正文留在授权仓库。带本地文档或 Host 安全策略的候选仍需接收方通过原 Host 安装与核验。

用项目或功能材料梳理流程时，可以请宿主调用 `flowkit_create_design_diagram`，只提供本次允许模型读取的文字材料。返回 `design.html` 与 `design.mmd`。点击节点可查依据，概览汇总材料摘要和待确认项。设计图不包含运行程序。需要推进任务时，从该设计起草可执行工作流、检查实际契约并完成候选复审。

真实验收从仓库根目录执行。第一条使用已登录的 Codex CLI。第二条在已配置 Responses 凭证和模型的环境运行。两条路线都会从自然语言起草，验证精确角色与 Skill，完成确认、签名三文件导出和实际 SDK 运行，并从本指南生成设计图。

```powershell
npm run build
node scripts/test-local-mcp-codex.mjs --live --verify-professional
node scripts/test-local-mcp-codex.mjs --live --verify-professional --openai
```

以“根据topic写草稿，经检查和审批再交付”为主线，先明确输入、结构化输出、审批必须由谁作出、失败/修订出口及终态判据。对应[完整Host例](/guide/host-integration)已有DSL/Skill/Runtime；[直接Host例](/examples/direct-host)继续关联编译JS、trace和最终state。

作者应先列业务验收，再选择 Standard 或适用的 Interactive 阶段，准备相应文件与 Host 方法。Standard 使用 `compile`、`compileSource` 或 CLI 编译检查，Interactive 使用 `compileInteractive`。执行者按选定 Host 路径核对输出、分支、副作用和失败处理。编译结果与业务验收分别记录。

## 图谱任务对应哪些说明

| 能力ID | 使用时先读 | 交付与限制 |
| --- | --- | --- |
| flowkit::define-workflow | [工作流模型](/guide/workflow-model)、[DSL](/dsl/index)、[JS/TS](/guide/javascript-typescript)、下表场景 | 静态字面量DSL；先选模式。八种Standard节点不等于P0-A全支持 |
| flowkit::compile-workflow | [compile/compileSource](/reference/sdk#compile)、[配置](/reference/options)、[产物](/guide/compile-artifacts) | code/可选Mermaid/diagnostics；compileSource接收DSL文本和filename，不接收自然语言，也不自动保存源码 |
| flowkit::check-workflow | [check](/reference/sdk#check)、[CLI](/reference/cli)、[诊断](/troubleshooting/compiler) | 只读诊断；没有compiled文件时无错误不等于已经构建；不比较Mermaid |
| flowkit::run-workflow | [Runtime](/reference/runtime)、[SDK](/reference/sdk#run)、[直接模块](/guide/direct-host)、[Interactive选型](/guide/interactive) | Host显式提供执行能力；不同接口层不混用。CLI没有run命令 |
| flowkit::render-mermaid | [编译产物](/guide/compile-artifacts)、[工作流模型](/guide/workflow-model) | 从合法DSL生成控制流图；不反向生成DSL，也不证明实际执行正确 |

取得Provider、listCatalog/getCapabilities/resolve和关闭Graph的方法见[能力声明](/guide/capability-provider)。Graph的requires表示能力依赖，不是工作流后继；解析成功不执行依赖或业务函数。DSL的agent是Skill映射，不能直接填图谱能力ID充当已有模型执行器。

需要业务能力时，由Host按[Graph绑定示例](/examples/capability-graph)显式解析并绑定执行。适用性、完整性与权限都需满足；缺绑定不能让模型自行编造实现。

## 场景、组合与必要Host能力

| 目标 | 当前可用路径与规则 | 应检查的结果/边界 |
| --- | --- | --- |
| 顺序或条件分流 | [模型](/guide/workflow-model)、[condition](/dsl/condition)；首个节点是入口，后继引用决定次序 | 只执行首个命中支路；默认路/输入缺失和布尔类型明确，不能把undefined随意当false |
| 结构化Agent生成 | [Agent](/dsl/agent)、[结果校验与重试](/guide/validation-retries) | inputs/Skill/Schema/重试次数；Host实现校验器。checkStep读取提交前state，verify读取候选state；P0-A不支持这两项Standard Agent能力 |
| 业务动作及判断 | [action](/dsl/action)、[verification](/dsl/verification) | Host有真实函数和写入责任；verification需boolean。声明writes不等于阻止所有外部副作用 |
| 同时做独立工作 | [parallel](/dsl/parallel)、[并行例](/examples/parallel-review) | 成员限Agent/action/verification单节点，不是任意子图。all_succeeded是Promise正常完成，any不取消剩余工作；false不等于reject |
| 有界检查修复 | [loop](/dsl/loop)、[修复例](/examples/verification-repair) | body是verification，失败修复链回到body；上限是检查次数。不能放parallel、嵌套loop或human修复链 |
| 人工决定及驳回 | [human](/dsl/human)、[审批例](/examples/human-approval) | 审批服务由Host提供；驳回链只能Agent/action并回同一human。不能用Agent自评宣称等价人工审批 |
| 错误、取消、观测与缓存 | [取消](/guide/cancellation)、[观测](/guide/observability)、[SDK缓存](/reference/sdk#run) | failed终点可正常resolve；异常/控制信号分开。取消需协作、trace需编译开启，编译缓存不是结果/进度恢复 |
| Skill和外部前提 | [本地](/guide/local-skills)、[远程](/guide/remote-skills) | 必要文件、白名单、完整性和读取权限；自定义loader承担相应责任，文档不是访问许可 |
| 交付编译JS | [AOT](/guide/aot)、[直接Host](/guide/direct-host) | 选择SDK或自供Ctx/Runtime；版本、源码/产物、Skill及结果组装准确，不借用未说明的上层依赖 |
| 暂停与持久续跑 | [Interactive](/guide/interactive)、[Host/Store](/guide/interactive-host-store) | 按 P0-A、P0-B、P1 或 P2 的节点能力起草，核对同一 Run 的请求、签收、授权和持久恢复 |
| 从图谱发现并执行业务能力 | [Provider](/guide/capability-provider)、[Host绑定](/examples/capability-graph) | 图谱依赖图与控制流图区分；绑定、上下文、依赖、权限与业务执行各有负责人 |
| 类型、复杂度与不支持目标 | [类型](/reference/types)、[结构/错误](/troubleshooting/compiler)、[兼容](/community/compatibility) | 字面量JS/可擦除TS、已定义/可达后继、字段及数量限制；编写时可生成文本，提交的DSL本身不能藏任意动态计算 |

复杂场景按**有业务意义的合法组合**验证，复用上述完整例；不要求所有模式交叉组合。需要当前不支持的语义时，说明具体限制，选择合适Standard路径或经用户认可的业务拆分；不能静默跳过审批/校验，或发明嵌套并行、自由回边、P0-B开关。

## 参数、状态和结果不能靠猜

每个输入写清来源、类型、是否必需和缺失处理；每个输出声明结构和业务含义。初始state、Agent提交、Action写入、Human决策及共享并行state各有规则，见[状态](/guide/state-data)。TypeScript推导有边界，readonly类型不构成运行隔离；Schema也不自动证明业务事实。

生成物应包括所选DSL、必要Skill/Host文件、依赖/版本、配置与回调来源、执行命令、成功/失败的可观察判据、资源清理和尚缺条件。概念片段可引用完整入口，但不能以未定义变量或隐藏函数充当完整教程。

## 验证和纠错顺序

先核角色/权限与版本，再核文件、绑定、模式和图；编译error先修，不使用失败后残留的旧产物。warning按其实际含义检查，例如分支可达输入与Host初始state，不能一概忽略或把所有warning说成执行失败。

用成功、相关业务失败和边界输入核对路线、尝试数、提交时点、状态与终态。类型和编译检验代码契约，自然语言意图由实际模型起草和语义复审验收。分别记录固定响应、真实模型、专家走读和真实用户证据。

读取不到对应版本文档、缺权限/Skill/绑定或业务约束不明确时，指出具体缺项并补信息；不从其它版本猜接口、虚构能力ID或把不可访问的页面当已读。当前站点内容与授权版本、支持矩阵共同核对，公开部署/Registry/技术门禁分别验收。

Author 引用选定能力的相应版本文档，保留 Provider 记录、内容摘要和验证结果，供后续核对。

当前站点针对1.0.0，没有按包版本切换的多版本路由。旧包不能只凭同一个URL把将来的最新内容当作自己的契约。后续发布应保留可取得的对应版本说明；Skill评估先记录实际文档版本/提交并与包核对，不能确认一致时停止依赖该说明生成，补齐受信版本材料后再继续。

## 作者任务的核对记录

后续评估Skill时，可选一个已有业务主线作为任务：只给定业务目标、输入和验收标准，记录作者实际能取得的文档与Host能力。先做批准路径，再选择与该目标有关的失败/缺信息条件；不要为覆盖率制造无限场景。下面是**评估记录模板**，不是新增API或DSL配置：

```text
业务目标、输入/权限与成功/失败判据：
FlowKit/Graph版本、运行环境、选定模式及理由：
实际可读的文档版本/提交、页面/锚点、必要文件：
Host已有能力、缺少的绑定/Skill/人工服务及处理方式：
作者/模型版本、任务说明、是否预先看过源码：
生成的DSL/Skill/Host文件及编译JS/图：
实际compile/check/类型检查命令、退出与diagnostics：
实际运行的输入、调用/分支/尝试、终态与业务结果：
与原业务判据的逐项对照、失败原因及需用户澄清事项：
证据文件/摘要、未验证项与保留的限制：
```

作者已经看过源码时标作专家或 AI 走读。固定响应验证接口和控制流。真实模型任务记录实际模型、提示及候选的复审和运行结果，真实读者另记参与者和任务结果。文档变化时重新验证受影响的场景。
