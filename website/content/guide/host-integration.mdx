# 接入自己的宿主

<a id="flowkit-doc-host"></a>

## Host 独立执行主体

长期 Host 可通过 `/host` 的 `configureCompilationCache`、`compilationCacheStatus` 和 `clearCompilationCache` 管理本进程的编译容量。它们影响该进程内的执行入口，不清理业务状态或卸载已加载 ESM。到驻留程序身份上限时轮换 Host 进程，详见 [SDK 缓存边界](/reference/sdk)。

完成 Run 且已保留持久回执后，Host 可调用 `releaseToolReceipts(ledger,{scope,runId})` 回收对应完成项。遇到 pending 或未知结果会整批拒绝清理，先对账；不会删除其他项目或 Run 的回执。

`/host` 的 `createIndependentAgentAdapter` 接收 Host 的 `select` 和 `authorize`，按 Artifact、Run 与 Node 绑定执行主体、会话、工作区和权限引用。Host 返回的 `IndependentAgentBinding` 执行 PreparedAgentTask。配置由 `IndependentAgentOptions` 描述。

需要独立复审的任务可用 `independentFrom` 提供实现者身份。重复主体、会话或工作区被拒绝。会话绑定按 Run 和 Artifact 保留，显式 `releaseRun` 只能释放已无实际执行的 Run。默认并发上限 4、会话绑定上限 64、单任务时限 30 秒，均可由 Host 配置。

超时与取消后，已启动且尚未结束的 Host 执行仍占容量。迟到结果不会变成已返回任务的成功。真正的会话创建、模型调用、独立凭据与工作区隔离由 Host 实现。普通单 Agent 工作流沿用原 Runtime 入口。

## 模型 API 工具循环

`@devcodex-labs/flowkit/host` 的 `createApiAgentAdapter` 接收 PreparedAgentTask，调用 Host 提供的 Responses 传输，再把输出交回统一 AgentExecutionResult。Host 为工具提供 schema、参数验证、授权、执行与副作用分类。写工具还提供稳定的业务 operation key，以回执识别重放和参数冲突。

工具循环默认最多 4 次 HTTP 请求、8 个 Tool Call、30 秒总时限。请求输入与 Provider 输出分别最多 256 KiB，参数和单个工具结果最多 64 KiB。单次输出上限 1024 tokens，累计观测 Token 上限 16000。429 和暂时性 5xx 最多按两次延迟策略重试，计入同一请求上限和 deadline。`ApiHostOptions.limits` 可由 Host 配置。金额预算仍由实际 Provider 和 Host 计费策略负责。

`supportsTools: false` 允许适用的预装配 JSON 任务。Host 用 `requiresTools` 标出必须动态工具执行的任务。未知写结果需要 Host 对账后处理，adapter 返回不自动重试的分类失败。`ApiHostTool` 的工具表与 `ledger` 由 Host 按项目和 Run 范围持有。

## MCP 宿主绑定

`flowkit_collection` 和协商的 Skills 发现按 `pageSize` 分页；使用 `nextCursor` 获取下一页。默认最多枚举 10000 条 metadata，可用 `maxMetadataEntries` 调整，每页还受 `maxResourceBytes` 限制。内置 Store 从 metadata 查询取得目录，只为选中页读取批准版本正文；自定义 Store 应提供 `readCollectionMetadata` 以避免全量正文装配。缩小集合范围可降低上下文与存储读取压力。

`@devcodex-labs/flowkit/mcp` 提供 `createFlowkitMcpServer`、`connectFlowkitStdio` 和 `createFlowkitHttpHandler`。Host 为每个连接或请求绑定项目 namespace、可访问集合、同一 Author 服务和批准版本存储。每次工具或资源操作均调用 Host 授权函数。

本地通过 stdio 连接。HTTP handler 由 Host 放进自己的服务，传入逐请求认证函数，返回 `authorHost.createMcpOptions(currentRequestContext, bindings)`。同一长期 AuthorHost 使用 namespace 独占的文件数据库保存草稿、回合和批准，不使用连接内候选 Map。每次请求都传当前主体、会话、工作区与授权集合；连接关闭不会关闭共享 AuthorHost。

`flowkit_start_workflow` 接收 `requestId`、明确的 create/update/import 操作和目标引用。`flowkit_prepare_workflow` 的 `inputRef` 由 Host 解析为准确 draftId、turnId、expectedStateVersion、当前输入及实际上下文，再调用同一 `advanceTurn`。查看差异需要 draftId/candidateHash/previousHash；发布还需最新状态版本、publicationId、真实 reviewRef 和用户 approvalRef。批准登记与保存可以在一个事务中完成。取消、对账和关闭由服务所有者使用 SDK；不增加 MCP 工具名。

工具覆盖起草、编译候选、查看差异、批准发布、丢弃候选、集合操作和运行。运行回调使用当前授权以及已批准 Artifact。Resources 使用包含 namespace、集合、Skill 和版本摘要的 URI。正文按需读取并受单次字节预算限制。

支持当前 MCP Skills 扩展的客户端可以分页查询 Skill metadata，并校验资源内容。普通客户端使用 Tools/Resources。工作流和专业 Skill 共用原来的两层集合及批准身份。

完整 Host 参数由 `FlowkitMcpOptions` 描述，`FlowkitMcpServer` 暴露连接和关闭生命周期。与模型运行、凭据和业务动作相关的实现由 Host 提供。

适用 FlowKit 1.0.0。先确定 Standard 或 Interactive 的能力范围，再提供相应类型的回调和授权。通过 Graph 发现能力后，仍由宿主提供动作绑定。

Runtime 是 FlowKit 与模型、审批界面、业务函数之间的接缝。本页把 Agent、Skill、输出 Schema、业务检查和人工审批放在一个完整例子里。示例使用固定响应，便于先确认编排正确，再替换真实服务。

## 选择运行模式

| 模式 | 入口和适用范围 |
| --- | --- |
| Standard | 使用根入口 `run`，在同一进程执行完整流程。下方示例覆盖 Agent 校验、验证和人工审批。 |
| Interactive P0-A | 内部候选通过 `@devcodex-labs/flowkit/interactive` 由可信 Host 调用。Agent、Condition 和 Terminal 可通过 SQLite 保存进度并在进程重启后续跑。Human、Action、Verification、Loop 和 Parallel 属于后续阶段。 |

Interactive 的 Host 负责持久化、模型隔离和权限检查。经 OS 认证的操作员会话绑定租户，完整结果由单独授权的审计角色读取。发行与部署状态以内部验收记录为准。 [Interactive 接入与完整示例](/guide/interactive)

## 按事件观察数据流

输出的 result.status 是 succeeded，terminal 是 done，state 包含 topic、draft 和 approval。events 的顺序是 agent → validate → checkStep → verify → human。checkStep 的 committed 为 false；verify 能读取候选 draft；human 能读取已经提交的 draft。

这个顺序解释了各层职责：Schema 检查结构，checkStep 检查业务限制，verify 检查候选结果，human 决定是否接受。三者不要都写成同一段无意义的“成功”判断。

## 替换真实 Agent

保留 runAgent 的参数结构，将固定返回值替换为你的模型调用。把 instruction 作为任务说明，把 input 作为业务输入，把 resultSchema 用于结构化输出或结果校验。使用 attempt 和 reasons 指导重试；把 signal 传给支持取消的网络客户端，把 runId 记入业务日志。

不要返回模型 SDK 的整个响应包装对象，应提取匹配 Schema 的业务对象。validateResult 必须同步返回 string[]；异步远程验证放在 checkStep 或 verify。示例校验器仅支持 draft 一个字段，增加 Schema 后必须同步升级校验器。

## 替换真实审批界面

runHuman 返回的 Promise 可以等待 Web 表单、桌面交互或队列响应。显示当前 draft，关联 runId，校验响应来自正确业务请求，再返回 boolean 或含 approved/comment 的对象。拒绝后 FlowKit 走 revise 动作，然后重新进入同一审批节点。

示例自动批准只用于演示。FlowKit 不提供账号权限、审批持久化、通知、跨进程等待或恢复服务；这些需要你的宿主负责。运行中等待 Promise 与可重启的持久化工作流是不同能力。

## 方法按实际节点提供

isControlSignal 始终必需。Agent 需要 runAgent 和 validateResult；action 需要 runAction；verification/Agent verify 需要 runVerification；human 需要 runHuman；condition 需要 evalWhen。默认 Skill loader 可直接使用，不必重新实现；自定义 loader 会接管其安全与缓存责任。

方法按 Runtime 对象调用，保留宿主 this 语义；不要在包装时随意丢失对象绑定。业务返回值不符合契约时，先修宿主，不要修改工作流绕过校验。完整签名和同步/异步边界见 [Runtime 契约](/reference/runtime)。

## 重复运行与排错

同一文件可多次调用 run。每次都有新 state/Ctx/默认 Skill loader；成功编译和加载的 DSL 可能命中进程内缓存，业务结果不会被缓存。Skill 文件改变会在下一次运行重新读取。完整缓存键、失败分类和长期进程边界见 [run](/reference/sdk#run)。

遇到本地 Skill 缺失先核对 projectRoot 和实际文件；输出不合 Schema 看 reasons；审批返回字符串会触发 FK_R002。修复后依次复验 compile、check、run，并确认事件顺序和结果状态。

## 使用 capability-graph 检查并绑定能力

若宿主需要 Provider 目录、适用性或跨 Provider 依赖检查，可使用[capability-graph 宿主消费示例](/examples/capability-graph)中的可选动作适配器。FlowKit 自身只负责执行工作流，不会自动执行 Graph 的 `requires` 依赖；宿主必须显式绑定被授权的动作。普通 `runAgent`/Skill 映射规则保持不变。


如需将编译JS交给已有JavaScript宿主，见[直接执行契约](/guide/direct-host)与[完整参考Host](/examples/direct-host)。SDK run/AOT仍是独立且正常的使用路径。
