# 状态与数据传递

state 是一次执行中节点交换数据的对象。设计工作流时先列出数据键、谁生产、谁消费，再画控制流，可以提前发现条件分支和并行写入问题。

## 初始状态是浅复制

`run(file, runtime, initialState)` 复制初始对象自己的、可枚举的字符串键到一个新对象。继承属性、Symbol 键和不可枚举属性不会成为顶层 state。嵌套对象仍是原引用；这里没有深复制、事务隔离或自动冻结。

```js
const initial = { topic: '入门', nested: { count: 0 } };
// 在runAction中：
ctx.state.topic = '新主题';       // 不修改 initial.topic
ctx.state.nested.count += 1;      // 会修改 initial.nested.count
```

需要隔离嵌套数据时，由宿主在调用 run 前按业务数据类型复制，例如对支持的纯数据使用 `structuredClone`。不要把共享数据库连接、请求对象或带副作用的 getter 当成普通 state 数据。

## Agent 只收到声明的输入

Agent 的 `inputs: ['topic', 'draft']` 从当前 state 选择这些键，放入 `step.input`。找不到的键登记在 `step.missing`，不会仅因缺键就自动中止；宿主可利用 missing 返回明确错误或补充默认值。初始输入无需伪造生产节点。

编译器的 `FK_C053` 是 warning：某键在流程内有声明的生产者，但在这个消费节点的所有到达路径上都没有生产。整个流程无人生产的键被视为宿主初始输入，不因此警告。静态分析不能证明外部输入一定存在，也不能完全验证 action 实际副作用。

## 写入发生在什么时候

| 来源 | 写入方式 | 应注意的边界 |
|---|---|---|
| Agent | result 通过 validateResult、checkStep、verify 后提交其自己的可枚举字符串键 | 失败尝试不提交顶层结果；校验器必须限制不允许的额外字段 |
| action | runAction 直接修改 ctx.state | writes 只是静态声明，不能代替赋值或阻止越界写入 |
| 并行中的 verification | 在 state[节点id] 写 boolean | 普通分支和 loop 内的 verification 直接控制路线，不自动写此键；false 不是 Promise 拒绝 |
| human | 在 state[节点id] 写 approved 和 comment | comment 未提供时归一为 null |
| condition/loop/parallel/terminal | 负责控制流 | 不提供独立的数据存储层 |

Agent 的 checkStep 看到提交前的 state。Agent verify 使用合并了候选结果的临时 state 视图，适合检查候选业务结果；verify 通过后才提交。嵌套对象仍可能共享引用，所以宿主校验函数应只读。

## 并行共享同一个 state

parallel 的各分支不是 state 快照。不要让分支依赖另一个分支尚未完成的写入。Agent output.properties、action.writes 和 verification id 等声明用于识别冲突；若两个分支声明写同一个键，编译器报 `FK_C026`。

即使声明键不同，两个分支也可能修改同一个嵌套对象，或者调用同一个外部服务。此类竞争需要宿主设计隔离、幂等键或锁。`join.strategy: 'any'` 完成后，其他分支仍可能继续写 state；如果后续步骤要求稳定的完整结果，使用 all_succeeded 并处理拒绝。

## 一次运行与下一次运行

每次 run 创建新顶层 state、Ctx 和默认 Skill loader。源码编译缓存不复用上一次业务 state，不保存审批结果，也不替你持久化进度。持久化数据库、运行记录和恢复策略属于宿主集成。

推荐为每个业务数据键记录来源、类型、允许覆盖的节点与缺失处理。先用[宿主示例](/guide/host-integration)观察 input/missing 和提交前后，再阅读[结果校验与重试](/guide/validation-retries)。
