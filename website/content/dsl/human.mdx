# human

`human(id, options)` 等待宿主取得人的批准或拒绝。拒绝后执行修订链并重新进入同一个审批节点；批准后才继续onApprove。

| 字段 | 类型/必需性 | 规则 |
|---|---|---|
| `name` | 必需string | 交给审批界面显示的名称 |
| `onApprove` | 必需节点id | 批准后的后继 |
| `onReject` | 必需节点 id | 修订链入口。通过修订检查后返回本 Human。 |
| `onDecline` | 节点 id，选填 | 启用三结果决策。拒绝终止或用尽修订次数时进入失败终点。 |
| `maxRevisions` | 0–100 的整数 | 三结果决策必填。限制实际启动的修订次数。 |

`id` / `name` 的合法值、唯一性及字符限制见[公共节点规则](/dsl/index#node-rules)；普通节点与并行成员的后继差异见[后继上下文](/dsl/index#successors)。

## 返回形状

声明 `onDecline` 时，Host 返回 `{ decision: 'approve' | 'revise' | 'decline', comment?: string | null }`。`approve` 继续，`revise` 进入修订并申请新的审核，`decline` 结束业务。进入同一 Human 的新审核有新的 `reviewDigest`。Interactive Host 需要校验审核摘要和审核主体。Standard 由提供 `runHuman` 的受信 Host 完成人员授权。

三结果修订区允许 Agent、Action、Verification 和 Condition。首次准备可以从同一个 `onReject` 入口进入，且不消耗修订次数。区内 Verification 的 `onFailure` 和 Interactive Action 的 `onError` 可以直接指向 Human 的 `onDecline` 失败终点，此时不发出新的审批请求。其余路径须返回同一个 Human，区外只能从 `onReject` 进入修订区。

修订超限进入失败终点并保留 `FK_R004`，显式拒绝直接走失败终点。通过普通回调提供布尔值会触发契约错误。

未声明 `onDecline` 的 Human 使用下面的批准与修订形式。

runHuman(name, ctx)异步返回boolean，或 `{ approved: boolean, comment?: string | null }`。无comment时归一为null。FlowKit在state[human节点id]保存这份决策，修订节点可读取comment。再次审批会覆盖该键，所以需要完整历史时由宿主另外存储。

```js
return { approved: false, comment: '请补充说明' };
```

字符串yes、数字1、approved缺失或非字符串comment都不合法，触发[FK_R002](/troubleshooting/runtime#FK_R002)。不要将HTTP状态或表单原始字符串直接作为审批结果。

## 拒绝链和等待边界

Standard 节点可设置 `maxRevisions` 为 0 到 100。计数针对实际启动的拒绝修订，达到上限时停止并抛出 `FK_R004`。

未声明 `onDecline` 时，修订链只能包含 Agent 和 Action，且必须回到同一个 Human。非法入口或修订节点可能触发 [FK_C060](/troubleshooting/compiler#FK_C060) 或 [FK_C061](/troubleshooting/compiler#FK_C061)。

Standard 的 `runHuman` 由宿主管理等待时限、取消和响应关联。Interactive 通过持久化检查点恢复待办，并在提交人工决定时校验权限和审核摘要。

## 验证和恢复

先compile/check验证拒绝链，再运行直接批准、拒绝修订再批准两条路径，确认state.approval和修订内容。故意返回 `'yes'` 应得到[FK_R002](/troubleshooting/runtime#FK_R002)；改回boolean或规范对象后复验。真实界面替换步骤与完整文件见对应场景页，取消约定见[取消与错误传播](/guide/cancellation)。

相关宿主方法：[runHuman](/reference/runtime#runHuman)、[runAction](/reference/runtime#runAction)。
